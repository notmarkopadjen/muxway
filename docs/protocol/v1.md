# Protocol v1

Everything a client needs to talk to a muxway hub. All examples use
placeholder names. Clients poll; the only push is the `wait` long-poll on
`/v1/events` and `/v1/admin/log`.

## Transport and authentication

- HTTPS only (a hub accepts plain HTTP on loopback alone, behind a proxy).
- Every client request carries `Authorization: Bearer <token>`. Tokens look
  like `mxt_` followed by 43 URL-safe characters and are issued by the hub
  owner with `muxway hub token create`, or by an admin with
  `POST /v1/admin/tokens`.
- A client names itself in `X-Muxway-Client` (a browser sends `web`), or
  failing that in the first word of its `User-Agent`: `muxway-android`,
  `muxway-midp`, `muxway-glasses-even`, and the same pattern for a new
  client. The hub shows the name to admins and nothing else depends on
  it.
- Clients whose network stack rewrites `Authorization` send the token in
  `X-Muxway-Token: <token>` instead. WAP 1.x phones are such clients: their
  stack knows only the Basic scheme and re-encodes a Bearer header as Basic.
  A request may carry both headers only if they hold the same token.
- Tokens never go in URLs.
- A page on another origin, such as a glasses app's WebView, may call the
  client endpoints with a bearer token: the hub answers CORS preflights on
  `/v1/hosts`, `/v1/panes`, `/v1/events`, `/v1/windows`, `/v1/transcribe`
  and `/v1/me` with
  `Access-Control-Allow-Origin: *`, the methods `GET` and `POST`, the
  headers `Authorization`, `X-Muxway-Token`, `Content-Type`, `Accept` and
  `If-None-Match`, and exposes `ETag`. It allows no credentials, so a
  session cookie is of no use to another origin, and the sign-in, agent
  and admin endpoints answer no preflight.
- **Peers** are the exception: the owner's other hubs, named on the
  command line (`muxway hub serve --peer https://work.example.com`,
  repeatable, an origin each). For a request whose `Origin` is exactly a
  peer, the preflight and the request are answered with
  `Access-Control-Allow-Origin: <that origin>`,
  `Access-Control-Allow-Credentials: true`, `Vary: Origin`, and
  `X-Muxway-Client` among the allowed headers, so a browser signed in
  here can use its session from the peer's web page. Every other origin
  keeps the wildcard without credentials. The web client's content
  security policy lets the page connect to the peers and nothing else new.
- A browser signs in once instead and gets a **session cookie**,
  `muxway_session` (HttpOnly, Secure, SameSite=Strict; SameSite=None on a
  hub with peers, so it travels to them). The hub honours it
  only when the request also carries an `X-Muxway-Client` header with any
  value. See [signing in](../features/sign-in.md).
- A hub may keep **address lists** (allow and deny). A request from an
  address they refuse is answered `403 forbidden` before anything else,
  credentials included. See [the admin overview](../features/admin.md).

## Responses

- JSON by default. Send `Accept: text/plain` for **text mode**, meant for
  small clients: no colours, tabs expanded, trailing blanks trimmed, lines
  rewrapped to `width`.
- Errors are `{"error": "<code>"}`:

| Status | Code | Meaning |
|---|---|---|
| 400 | `bad_json`, `bad_input`, `bad_parameter` | malformed request, text with control characters, unknown key, parameter out of range |
| 401 | `unauthorized`, `sign_in_failed` | missing, wrong, expired or revoked token (never says which); the identity provider's answer did not verify |
| 403 | `read_only`, `no_account`, `forbidden` | the pane is readable but the token or the pane's mark does not allow writing; a verified identity with no user on this hub; the address lists refuse the client, or an admin endpoint was called without the admin grant |
| 404 | `not_found` | no such host or pane, **or one the token may not see** |
| 409 | `exists`, `too_many`, `self_lockout` | see the endpoint |
| 413 | `too_large` | body over 16 KiB (a file: over 8 MiB) |
| 415 | `unsupported` | a file of a type the inbox does not take, or not what its type says |
| 429 | `locked_out`, `rate_limited` | 10 failed authentications from an address in 10 minutes lock it for 10 minutes; a token may make 20 requests per second, in bursts of up to 40 |
| 502 | `provider_unavailable` | the identity provider could not be reached |
| 503 | `host_offline` | the host's agent is not connected |
| 507 | `inbox_full` | the host's inbox holds 500 files or 256 MiB |

## Signing in

| Method and path | Purpose |
|---|---|
| `GET /v1/auth` | no authentication; `{"methods": ["token", "oidc"], "oidc": {"label": "Sign in with Example"}}`; `methods` is `["token"]` on a hub without a provider |
| `POST /v1/auth/token` | `{"token": "mxt_..."}`; sets the session cookie; `204`, or `401` which counts toward the lockout |
| `GET /v1/auth/oidc/start` | redirects to the identity provider |
| `GET /v1/auth/oidc/callback` | the provider's return; sets the cookie and answers a page that continues to `/` (a redirect would still be a cross-site navigation, on which browsers withhold a `SameSite=Strict` cookie); `401 sign_in_failed`, `403 no_account` or `502 provider_unavailable` |
| `POST /v1/auth/logout` | ends the session; `204` |
| `GET /v1/me` | `{"id": "0ddba4b5", "name": "phone", "method": "token", "read": [...], "write": [...], "expires": 1767225600}` |

`method` is `token` for a pasted token or the provider's name; `expires` is
when the session ends; `"admin": true` is there only for a principal with
the admin grant. Every endpoint below accepts the session cookie
with the header in place of the bearer token.

## Addresses

`<host>/<session>/<window>.<pane>`: host alias (`[a-z0-9-]{1,32}`), session
name, window index or name, pane index. Session and window names in a
request may use `[A-Za-z0-9._-]{1,64}`; a name with other characters is
reached by window index. A pane with an alias is also `<host>/@<alias>`.

## Endpoints

### `GET /v1/hosts`

Hosts the token has a read grant on, whether connected or not.

```json
{"hosts": [{"name": "alice-laptop", "online": true, "sessions": true, "keys": 2, "repeat": true}]}
```

`sessions` is present, and true, when the host's agent runs with
`--allow-sessions`, so a client may start a session there (see
`POST /v1/hosts/{host}/sessions`); `close` likewise when it runs with
`--allow-close`, so a client may close panes there (see
`POST /v1/panes/{address}/close`); `preview` likewise when it runs with
`--preview`, so a writer may read files a pane prints the paths of (see
`GET /v1/panes/{address}/preview`) and see the changes of the repository
a pane works in (see `GET /v1/panes/{address}/git`). `keys` is the key names the host's
agent takes: `2` for the grammar under `input`, absent for the earlier
list; `repeat`, present and true, says the agent takes a `count` with a
key. Text mode: `alice-laptop<TAB>online`
per line.

### `GET /v1/panes`

Every pane the token can read, on every connected host, sorted by host,
session, window and pane.

```json
{"panes": [{
  "host": "alice-laptop", "address": "alice-laptop/work/1.0",
  "session_id": "$0", "session": "work",
  "window_id": "@1", "window_index": 1, "window": "logs",
  "window_layout": "b25d,100x30,0,0,1", "window_active": true,
  "pane_id": "%3", "pane_index": 0, "pane_active": true,
  "width": 100, "height": 30, "title": "build", "command": "bash",
  "activity": 1767225600, "mode": "write", "alias": "logs",
  "cursor_x": 3, "cursor_y": 30
}]}
```

`mode` is what *this token* may do: `write` only when both the pane's mark
and the token allow it. `cursor_x` and `cursor_y` are the cursor's cell,
1-based, where the program waits for input, so a client can draw it or
treat a click on that row as a wish to type; absent from an older agent,
and dropped by the hub when outside the pane's size. `window_layout` is tmux's layout string for the
window. A pane that needs its owner also carries
`"attention": {"kind": "question", "at": 1767225600, "text": "..."}` with
`kind` one of `question`, `permission`, `idle`, `done`; see
[notifications](../features/notifications.md). Text mode:
`<address><TAB><mode><TAB><command><TAB><title><TAB><kind>`, the last
column empty when nothing is pending. `title` is what the program in the
pane calls itself (tmux's pane title), `command` the program's name. Text
mode takes `charset` as a pane read does: `command` and `title` are
rewritten for the charset and the body is encoded in it; the other
columns are ASCII already.

### `GET /v1/hosts/{host}/tree`

One host as sessions, windows (with layout) and panes, nested:

```json
{"host": "alice-laptop", "sessions": [{"name": "work", "windows": [
  {"index": 0, "name": "editor", "layout": "...", "active": false, "panes": [ ... ]}
]}]}
```

### `GET /v1/panes/{address}`

Query: `lines` (1 to 2000, default 100), `width` (8 to 400, default 80,
text mode), `charset` (text mode: `utf-8`, the default, `latin1` or
`ascii`), `ansi=1` (JSON only: keep the escape sequences tmux's
`capture-pane -e` writes, colours and OSC 8 hyperlinks among them; a
client drops any sequence it does not read).

```json
{"pane": { ...as in the list... }, "content": "$ make test\nok\n$ ", "trimmed": 27}
```

In JSON, `content` is the pane's last `lines` rows as the terminal shows
them, one row per line, a line the terminal wrapped at the pane's width
on as many rows as it took; draw it row for row. Blank rows at the
bottom of the screen are left out and `trimmed` counts them, so the
screen is the content's last `height - trimmed` rows and a row of the
content maps to a row of the pane (for a click, or the cursor's row).
A hub before this field leaves it out: take it as 0. Text mode joins such a
line back into one and returns the last `lines` lines after rewrapping. With `latin1`
or `ascii` the hub first rewrites what the charset cannot carry (see
[text mode](../features/text-mode.md)): box-drawing lines become `-`,
`|` and `+`, bullets `*`, arrows `>` and `<`, letters lose the marks the
charset lacks, and the rest becomes `?`. The body is then encoded in that
charset and `Content-Type` names it: `text/plain; charset=utf-8`,
`charset=iso-8859-1` or `charset=us-ascii`. A hub without this
parameter ignores it and answers UTF-8, so decode by the `Content-Type`
you receive. Responses carry an `ETag`; send it back in `If-None-Match`
to get `304` when nothing changed, which keeps polling cheap on slow
links.

### `POST /v1/panes/{address}/input`

Body, exactly one of:

```json
{"text": "make test"}
{"key": "Enter"}
{"mouse": {"button": "left", "x": 12, "y": 3}}
```

- `text`: UTF-8, 1 to 4096 bytes, no control characters (C0, DEL, C1),
  except the newline. A text without a newline is typed literally. A text
  with one is **pasted**: the agent loads it into a tmux buffer and pastes
  the buffer into the pane, wrapped in the bracketed-paste marks when the
  program asked for them (`ESC [ 200 ~` … `ESC [ 201 ~`, written by tmux,
  never accepted from a client), so Claude Code or a readline shell takes
  the lines as one block and waits; a program that did not ask gets the
  bytes as typed, and a shell without bracketed paste runs each line at
  its newline. Send `Enter` separately either way. Carriage return and
  tab stay refused. A hub older than this answers `400 bad_input` to a
  newline.
- `key`: a key by name, from this grammar and nothing else:

  ```
  key    = [ "C-" ] [ "M-" ] [ "S-" ] base       ; Ctrl, Alt (Meta), Shift: this order, each once
  base   = named | keypad | char
  named  = Enter | Tab | BTab | BSpace | Escape | Space | Up | Down | Left | Right
         | PageUp | PageDown | Home | End | Insert | Delete | F1 … F12
  keypad = KP0 … KP9 | KP/ | KP* | KP- | KP+ | KP. | KPEnter
  char   = a … z | 0 … 9 | ` | - | = | [ | ] | \ | ' | , | . | /   ; with C- or M-, never S-
  ```

  A `char` goes with Ctrl or Alt only: alone, or shifted, it is `text`.
  `;` is not a `char`, because tmux would read it as the end of a
  command; there is no F13: terminals send it as Shift+F1, so send
  `S-F1` (to `S-F12` for F24). At most 16 bytes. The names are tmux's
  (`Insert` and `Delete` reach it as `IC` and `DC`); `BTab` is Shift-Tab,
  which AI coding CLIs use to cycle their modes. Examples: `C-c`,
  `C-M-Delete` (`ESC [3;7~`), `S-Up`, `M-S-F5`, `M-x`, `KP7`. A host
  whose agent takes the grammar lists `"keys": 2`; an older one, or an
  older hub, answers `400 bad_input` to anything beyond the earlier list
  (the named keys, `C-c` `C-d` `C-z` `C-l` `C-a` `C-e` `C-u` `C-k` `C-w`
  `C-r` `C-x` `C-n` `C-p` `C-f`).

  ```http
  POST /v1/panes/alice-laptop/work/0.0/input
  {"key": "C-M-Delete"}
  → 204
  {"key": "C-;"}
  → 400 {"error": "bad_input"}
  ```
- `count`, with `key` only: the key is sent that many times in one
  request, 1 to 50, so a key held in a client's direct typing is a few
  requests rather than one per repeat; absent, once. With `text` or
  `mouse`, or out of range, `400 bad_input`. A host whose agent takes it
  lists `"repeat": true`; to an older host a client sends the key once
  per press.

  ```http
  POST /v1/panes/alice-laptop/work/0.0/input
  {"key": "Down", "count": 5}
  → 204
  {"key": "Down", "count": 51}
  → 400 {"error": "bad_input"}
  {"text": "a", "count": 2}
  → 400 {"error": "bad_input"}
  ```
- `mouse`: a click, press and release, or wheel notches, at a cell of
  the pane: `button` one of `left`, `middle`, `right`, `wheelup`,
  `wheeldown`; `x` and `y` 1-based, within the pane's width and height;
  `count`, with the wheel buttons only, turns the wheel that many
  notches in one request (1 to 50; absent, one), so a long scroll is a
  few requests rather than one per row.
  It reaches the program only when it asked its terminal for the mouse:
  the listing says so with `"mouse": true`, and the agent answers
  `bad_input` otherwise, so the bytes are never typed as text. The agent
  writes the xterm sequence in the encoding the program chose, SGR or
  the old one (which reaches cell 223 at most).

Answers `204` on success. A hub without mouse input answers `400
bad_json` to the third shape.

### `GET /v1/events`

Notifications from panes the token may read, oldest first. Query: `after`
(the `next` of the previous answer; without it, the most recent events),
`wait` (0 to 30 seconds to hold the request until an event arrives,
default 0), `limit` (1 to 100, default 50).

```json
{"events": [{
  "seq": 12, "at": 1767225600,
  "host": "alice-laptop", "address": "alice-laptop/work/1.0",
  "pane_id": "%3", "alias": "build",
  "kind": "permission", "text": "Claude needs your permission to use Bash"
}], "next": 12}
```

- `kind` is `question`, `permission`, `idle`, `done` or `working`; the last
  clears the pane's attention.
- `next` is the cursor for the next call, also when `events` is empty. A
  cursor the hub does not know (it restarted) counts as absent.
- With `wait`, the answer comes as soon as there is an event the token
  may see, or empty when the time is up.
- Text mode: `<seq><TAB><at><TAB><address><TAB><kind><TAB><text>` per
  event, then `next<TAB><seq>`.

### `GET /v1/transcribe` and `POST /v1/transcribe`

Spoken clips to text, for clients with a microphone: the glasses, the
browser and the phone among them. A hub has a transcriber only when its
owner configured one (`muxway hub
serve --stt-url ...`, see [transcription](../features/transcription.md));
`GET` answers `204` when it has one and `404 not_found` otherwise, so a
client knows whether to offer the action.

`POST` takes `Content-Type: audio/wav`, a 16 kHz mono 16-bit PCM WAV of
at most 4 MiB and at least half a second, from a principal with at least
one write grant (the text exists to be typed). The hub forwards the clip
to the transcriber and answers the text it heard, cleaned of control
characters and cut to 4096 bytes, which is what input takes:

```json
{"text": "run the tests again"}
```

Text mode: the text, one line. Errors: `400 bad_input` (not such a WAV,
or too short), `403 read_only` (no write grant), `404 not_found` (no
transcriber), `413 too_large`, `429 rate_limited` (one clip per five
seconds per principal, on top of the general limit), `502
provider_unavailable` (the transcriber failed or took over 90 s). The
clip is kept in memory for the request only; the audit log records who,
how many bytes and seconds, and the result, never the text.

### `POST /v1/panes/{address}/resize`

Sizes the pane on the host, as a terminal would, or gives it back to
tmux. Body, exactly one of:

```json
{"cols": 140, "rows": 32}
{"cols": 140, "rows": 32, "scope": "window"}
{"cols": 140, "rows": 32, "scope": "window", "layout": "b25d,1000x1000,0,0[1000x750,0,0,3,1000x250,0,0,4]"}
{"cols": 140, "rows": 32, "scope": "window", "zoom": true}
{"fit": "auto"}
```

Without a scope, or with `"scope": "pane"`, the **pane** becomes
`cols × rows`: on an axis the pane spans its window, the window is sized;
on an axis it shares with neighbours, they give or take, and the window
grows before any pane of it would go under 20 columns or 5 rows. The
host keeps the size each pane of the window was given this way and
gives it again when another pane of the window is fitted, the pane
asked for last winning where two cannot both be had; a window fit or a
release forgets them. A pane fit undoes the window's zoom. A window
whose fitting panes are all gone (their shells exited) is given back by
the host on its next listing, since no client can release it through
them any more. With
`"scope": "window"`
the pane's whole **window** is sized and its panes keep the proportions
they had (tmux's own resize would not keep them), or, with a `layout`,
take the proportions of that layout: a tmux layout string (as the window
endpoint returns it) whose sizes are read as weights and scaled to
`cols × rows`, so a client sends the splits it shows, in any unit. The
layout must name exactly the window's panes, is at most 2048 bytes, and
goes with the window scope only. Its pane ids are honoured: each pane
goes where the layout names it (tmux itself would fill the places in its
own pane order, so the agent swaps the panes into the layout's order
first). A layout that moves panes, a shape other than the window's, needs
a write grant on every pane of the window, `403 read_only` otherwise;
moving changes the panes' indexes, so their addresses, and the answer
then lists them all under `panes`. A layout with no `cols` and `rows`
arranges the window at the size it has:

```json
{"scope": "window", "layout": "0000,1000x1000,0,0{500x1000,0,0[500x500,0,0,4,500x499,0,501,5],499x1000,501,0,3}"}
→ 200 {"pane": {...}, "panes": [{"address": "alice-laptop/work/0.0", "pane_id": "%4", ...}, ...]}
``` With `"zoom": true`, window scope only,
the pane is then shown alone in its window, as tmux's own zoom does; a
window resize without it undoes a zoom. The listing marks the pane shown
alone with `"zoomed": true`; its size is then the window's, the layout
string still the one underneath. `fit: auto` releases all of it: the
window returns to automatic sizing, unzoomed, and the panes to the proportions
they had before the first resize, unless they were moved since: then they
stay where they are.

Needs a write grant and a pane marked for writing, like input: the person
at the host sees the change. `cols` 20 to 500, `rows` 5 to 300. Answers
`200` with `{"pane": {...}}` as the listing shows the pane afterwards,
`400 bad_parameter`, `403 read_only`, `404`, `429 rate_limited` for more
than one resize per second on the same window, or `503`.

### `GET /v1/windows/{host}/{session}/{window}`

One window, every pane of it the principal may read, with content, in one
request. Query `lines` (1 to 2000, default 100) and `ansi=1`.

```json
{"host": "alice-laptop", "session": "work",
 "window": {"index": 1, "name": "logs", "layout": "b25d,100x30,0,0{50x30,0,0,3,49x30,51,0,4}", "active": true},
 "panes": [{"pane": {...}, "content": "..."}]}
```

`layout` is tmux's layout string: a checksum, then cells `WxH,X,Y` that are
a pane (`,id`) or a split with children in `{...}` (side by side) or
`[...]` (stacked). A pane outside the grants is absent from `panes` but
still named in the layout. Carries an `ETag`; `304` on `If-None-Match`.
JSON only.

### `POST /v1/windows/{host}/{session}/{window}/panes`

Adds a pane to the window, as `tmux split-window` would. Body:

```json
{"direction": "h"}
```

`h` puts the new pane beside the pane it is split from, `v` below it. The
source is the window's active pane when the principal may type into it,
else the first pane of the window it may; the new pane opens in the
source's directory with the host's shell, and the host's focus stays where
it was. A mark set on the source pane itself is copied onto the new pane;
a mark on the window or session covers it already. The principal then
needs a write grant that covers the **new** pane's address: when it does
not, the hub closes the pane again and answers `403 read_only`, so a grant
for `alice-laptop/work/1.0` alone never gets a sibling.

Answers `201` with `{"pane": {...}}` as the listing shows the new pane,
`400 bad_input`, `403 read_only` (no writable pane in the window, or the
new pane outside the grant), `404 not_found`, `409 too_many` when the
window has 8 panes, `429 rate_limited` for more than one creation (pane or
session) per two seconds by the same principal, a refused one included, or
`503 host_offline`.

### `GET` and `POST /v1/panes/{address}/files`

A file for the program in a pane, written on its host, when the host's
agent runs with `--inbox`. `GET` answers `204` when the pane takes files
(a client shows its button), else `403 read_only` or `404 not_found`.

`POST` is `multipart/form-data` with one part named `file`; the part's
`Content-Type` is the file's type, one of `image/png`, `image/jpeg`,
`image/gif`, `image/webp`, `application/pdf`, `text/plain`,
`text/markdown`, `application/json`, `application/zip`. A binary type must sniff as itself; a
text type must be UTF-8 without control bytes but tab, newline and
return; JSON must parse. At most 8 MiB. The part's file name is ignored:
the agent names the file. The principal needs a write grant on the pane,
the pane a writable mark; one file every two seconds per principal (a
refused one costs nothing).

```http
POST /v1/panes/alice-laptop/work/0.0/files
Content-Type: multipart/form-data; boundary=x

--x
Content-Disposition: form-data; name="file"; filename="file"
Content-Type: image/png

<the PNG's bytes>
--x--
```

Answers `201 {"path": "/home/alice/.config/muxway/agent/inbox/20261025-102235-56fwge.png", "bytes": 48213}`,
`400 bad_input` (not one `file` part), `403 read_only`, `404 not_found`
(also when the agent takes no files), `413 too_large`, `415 unsupported`,
`429 rate_limited`, `503 host_offline` or `507 inbox_full`. The client
puts the path on its input line; nothing is typed into the pane.

### `GET /v1/panes/{address}/preview?path=…`

A file a pane printed the path of, for a principal with a write grant
on a writable pane, on a host whose agent runs with `--preview <dir>`:
a client shows it in a window. `path` is the path as printed, up to
1024 bytes, no control characters, else `400 bad_input`. The agent
resolves it from the pane's current directory (`~` from its home) and
serves it only when it lies under a root once every symlink is followed,
with no dot component below the root, as a regular file of at most 8
MiB whose extension is one of `txt md markdown csv tsv json log yaml yml
toml ini xml html js jsx ts tsx cs go py rb rs java kt kts c h cpp hpp sh
bash zsh fish sql css scss less` (served as `text/plain; charset=utf-8`),
`png jpg jpeg gif webp` (as themselves) or `pdf`. Answers `200` with the bytes and the
headers of `files/{name}` below; `403 read_only`; `404 not_found` for
anything the host will not serve, one code whether the file is missing,
hidden, outside a root, of another type or the host has no roots; `429
rate_limited` above two a second per principal, with a burst of five;
`503 host_offline`.

```http
GET /v1/panes/alice-laptop/work/0.0/preview?path=docs%2Fplans%2Fa.md
```

### `GET /v1/panes/{address}/git`

Git's view of the repository the pane works in, for a principal with a
write grant on a writable pane, on a host whose agent runs with
`--preview <dir>`: a client shows it as a tree. The agent walks up from
the pane's current directory to the nearest `.git` and answers only when
that root lies under a preview root (symlinks followed, no dot component
below the root), from a read-only `git status`. Answers `200` with

```json
{
  "root": "/home/alice/work/muxway",
  "branch": "main",
  "ahead": 1,
  "entries": [
    {"path": "src/a.go", "kind": "modified"},
    {"path": "src/new.go", "kind": "added", "staged": true},
    {"path": "src/moved.go", "from": "src/old.go", "kind": "renamed", "staged": true},
    {"path": "src/gone.go", "kind": "deleted"},
    {"path": "notes.txt", "kind": "untracked"}
  ]
}
```

`kind` is one of `added modified deleted renamed untracked conflict`;
`from` only on a rename; `ahead` and `behind` against the upstream when
there is one; `"truncated": true` when more than 2000 entries were left
out. `Cache-Control: private, no-store`. `403 read_only`; `404
not_found` for anything the host will not show, one code whether the
pane's directory is in no repository, the repository is outside the
roots, the host has no roots or no git; `429 rate_limited` above one a
second per principal, with a burst of six; `503 host_offline`.

```http
GET /v1/panes/alice-laptop/work/0.0/git
```

### `GET /v1/panes/{address}/git/diff?path=…`

One change's diff against the last commit, for the same principal and
pane. `path` is a path as the status above listed it, up to 1024 bytes,
no control characters, else `400 bad_input`; an untracked path, a path
the status does not list, or anything else the host will not show is
`404 not_found`. Answers `200` with `{"diff": "<unified diff>",
"binary": false, "cut": false}`: `binary` when git has no text for the
change, `cut` when the diff was longer than 1 MiB and was cut there. A
client draws the diff as text. `429 rate_limited` above two a second per
principal, with a burst of five.

```http
GET /v1/panes/alice-laptop/work/0.0/git/diff?path=src%2Fa.go
```

### `GET /v1/panes/{address}/files/{name}`

One file of the inbox back, by the name the agent gave it, for a
principal that may read the pane: a client shows an image whose path a
program printed. `name` is exactly one inbox file name,
`^[0-9]{8}-[0-9]{6}-[a-z0-9]{6}\.(png|jpg|gif|webp|pdf|txt|md|json|zip)$`;
anything else is `400 bad_input` before the host hears of it, so no
path ever travels. Answers `200` with the bytes, `Content-Type` by the
extension (the images, the PDF and the zip as themselves, `txt`, `md` and
`json` as `text/plain; charset=utf-8`), `Content-Disposition: inline`,
`X-Content-Type-Options: nosniff` and `Cache-Control: private,
no-store`; `404 not_found` when there is no such pane, no inbox on the
host or no such file; `429 rate_limited` above one read a second per
principal, with a burst of three; `503 host_offline`.

```http
GET /v1/panes/alice-laptop/work/0.0/files/20261025-102235-56fwge.png
```

### `POST /v1/panes/{address}/close`

Closes the pane on its host, ending whatever runs in it, when the host's
agent runs with `--allow-close`. No body (or `{}`). The principal needs a
write grant on the pane, and the pane must be marked for writing. Shares
the creation rate limit: one per two seconds per principal.

Answers `204`, `400 bad_json`, `403 read_only`, `404 not_found` (also
when the agent does not close panes), `429 rate_limited` or `503
host_offline`. tmux renumbers the window's other panes at once, so a
client drops the address and reads the listing again.

### `POST /v1/hosts/{host}/sessions`

Starts a detached session with the host's shell, when the host's agent runs
with `--allow-sessions`. Body:

```json
{"name": "scratch"}
```

The name is `[a-z0-9_-]{1,32}` and must not exist. The agent marks the
new session `@muxway-mode = write`, so it is exposed like any other and
`muxway exposed` lists it. The principal needs a write grant that covers
`host/<name>/*` (checked on the name before asking, and on the first pane
after).

Answers `201` with `{"pane": {...}}`, the session's first pane, `400
bad_input`, `403 read_only`, `404 not_found` when the host does not start
sessions, `409 exists`, `409 too_many` after 32 sessions started this way
that still live, `429 rate_limited` as above, or `503 host_offline`.

## Admin

Not for ordinary clients: these need a principal with the admin grant
(`--admin` on `muxway hub token create` or `user create`) and answer
`403 forbidden` to any other. They take the bearer token or the session
cookie with the client header, and answer no CORS preflight. See
[the admin overview](../features/admin.md).

| Method and path | Does |
|---|---|
| `GET /v1/admin/overview` | the hub's facts, agents, tokens, users, clients, locked addresses, the address lists, and the caller's address as the hub sees it |
| `GET /v1/admin/log?after=N&limit=200&wait=0` | log records after `N` (without `after`, the latest), `limit` 1 to 500, long-polled up to `wait` seconds (at most 30) like `/v1/events` |
| `POST /v1/admin/tokens` | `{"name", "read", "write", "ttl", "admin"}`, `ttl` in seconds (0: 30 days, or 24 h with `admin`); `201 {"secret", "token"}`, the secret only here |
| `DELETE /v1/admin/tokens/{id}` | revoke; its sessions end at once; `204` or `404` |
| `POST /v1/admin/users` | `{"email", "name", "read", "write", "ttl", "admin"}`; `201 {"user"}` |
| `DELETE /v1/admin/users/{id}` | remove; its sessions end; `204` or `404` |
| `DELETE /v1/admin/sessions/{id}` | end one browser session, named by its `id` in the overview; `204` or `404` |
| `PUT /v1/admin/access` | `{"allow": [...], "deny": [...]}`, CIDRs or addresses, at most 256 each, body up to 64 KiB; answers the stored, normalised lists; `400 bad_input`; `409 self_lockout` when the caller's own address would be refused, unless `?force=1` |
| `POST /v1/admin/unlock` | `{"addr"}` lifts a lockout; `204`, `400`, or `404` when it was not locked |

## Agent channel

For agent implementers only; clients never see it.

- `POST /v1/pair` with `{"code_id", "host", "agent_key", "proof"}` where
  `proof = base64url(HMAC-SHA256(secret, "muxway-v1-pair\0" + host + "\0" + agent_key_bytes))`.
  The answer `{"sig"}` is the hub's Ed25519 signature over
  `"muxway-v1-paired\0" + host + "\0" + agent_key_bytes`.
- `GET /v1/agent` upgrades to a WebSocket of binary messages. Handshake:
  `hello {v, nonce, eph}` from the hub; `{host, nonce, eph, sig}` from the
  agent; `{sig}` from the hub. Signatures are Ed25519 over
  SHA-256(`"muxway-v1-agent\0"` or `"muxway-v1-hub\0"`, host, `\0`, then hub
  nonce, hub ephemeral key, agent nonce, agent ephemeral key, each prefixed
  with its 4-byte big-endian length). Keys: HKDF-SHA256 over the X25519
  secret, salt = hub nonce + agent nonce, info `muxway-v1 hub to agent` and
  `muxway-v1 agent to hub`, 32 bytes each, AES-256-GCM with a 96-bit nonce
  that is a per-direction counter starting at 0.
- Then the hub sends `{"id", "op": "list" | "read" | "input" | "resize", "actor",
  "pane", "lines", "ansi", "wrapped", "text", "key", "count", "mouse"}` and the agent answers
  `{"id", "error", "panes", "content"}` with error codes `not_exposed`,
  `read_only`, `bad_input`, `unknown_op`, `tmux_error`. A `read` with
  `wrapped` true gets the rows as the terminal wrapped them; without it,
  as before, a wrapped line comes back joined, for the hub's text mode to
  rewrap. An agent from before the field joins either way.
- `resize` is a fourth op: `{"id", "op": "resize", "actor", "pane",
  "cols", "rows", "scope", "layout", "arrange", "zoom"}` (`scope` absent
  or `"pane"`, or `"window"`; `layout`, `arrange` and `zoom` only with
  `"window"`) or `{..., "fit": "auto"}`, answered like `input`, with
  `rate_limited` among the errors. The agent checks the layout itself: it
  parses and names the window's panes, no more and no fewer, or the
  answer is `bad_input`. `arrange` is true when the hub found the
  principal may write to every pane of the window, so the layout may move
  panes and not only size them; the agent checks that against the live
  window too, and both audit it.
- `split`, `new-session` and `kill-pane` make and unmake panes:
  `{"id", "op": "split", "actor", "pane", "direction": "h" | "v"}` splits
  an exposed, writable pane and answers `{"id", "pane": <the new pane as
  listed>}`, or `read_only`, `too_many` (8 panes in the window),
  `bad_input`; `{"id", "op": "new-session", "actor", "name"}` answers the
  session's first pane, or `not_allowed` (the agent runs without
  `--allow-sessions`), `exists`, `too_many` (32 live sessions it started),
  `bad_input`; `{"id", "op": "kill-pane", "actor", "pane"}` closes a pane
  the agent made within the last 30 seconds and nothing else
  (`not_exposed` otherwise). An agent that starts sessions says so with
  `"sessions": true` in every `list` answer.
- `{"id", "op": "file", "actor", "pane", "type", "data"}` (`data` in
  base64) writes a file for a writable exposed pane into the agent's
  inbox and answers `{"id", "path"}`, or `not_allowed` (no `--inbox`),
  `read_only`, `bad_input` (not what its type says), `inbox_full` (500
  files or 256 MiB). This message may be up to 12 MiB; every other stays
  under 1 MiB. An agent with an inbox says so with `"inbox": true` in
  every `list` answer.
- `{"id", "op": "read-file", "actor", "pane", "name"}` answers
  `{"id", "type", "data"}` (`data` in base64) for one file of the inbox
  by name, for an exposed pane, or `not_allowed` (no `--inbox`),
  `bad_input` (not an inbox name), `no_file` (no regular file of that
  name, a symlink included). The answer may be up to 12 MiB like a
  file's own message.
- `{"id", "op": "read-path", "actor", "pane", "path"}` answers
  `{"id", "type", "data"}` for a file the pane printed the path of,
  resolved from the pane's current directory (`~` from the agent's
  home) and lying under one of the agent's `--preview` roots once every
  symlink is followed, with no dot component below the root, a regular
  file of a type a window shows, at most 8 MiB; or `not_allowed` (no
  roots), `no_file` (everything else, one code). An agent with roots
  says so with `"preview": true` in every `list` answer.
- `{"id", "op": "git-status", "actor", "pane"}` answers `{"id",
  "changes": {"root", "branch", "ahead", "behind", "truncated",
  "entries": [{"path", "from", "kind", "staged"}]}}` for the repository
  the pane's current directory lies in, when its root (the nearest
  `.git` walking up) lies under one of the agent's `--preview` roots once
  every symlink is followed, with no dot component below the root, from
  `git status --porcelain=v2 --branch --untracked-files=all -z` run
  read-only (`--no-optional-locks`, a fixed argument list, a clean
  environment, no hooks, no pager, no external programs, a ten second
  timeout); or `not_allowed` (no roots), `no_file` (everything else, one
  code). At most 2000 entries, then `truncated`.
- `{"id", "op": "git-diff", "actor", "pane", "path"}` answers `{"id",
  "diff", "binary", "cut"}` from `git diff --no-color --no-ext-diff
  --no-textconv HEAD -- <path>` for a path a fresh status lists (not an
  untracked one), run as above; at most 1 MiB, then `cut`; or
  `not_allowed`, `bad_input` (a path with a control character),
  `no_file`.
- `{"id", "op": "close-pane", "actor", "pane"}` closes an exposed,
  writable pane for a client, or answers `not_allowed` (the agent runs
  without `--allow-close`), `read_only`, `not_exposed`. An agent that
  closes panes says so with `"close": true` in every `list` answer, one
  that takes the key grammar with `"keys": 2`, and one that takes a
  `count` with a key (1 to 50, `send-keys -N`) with `"repeat": true`.
- The agent may also send, unasked, `{"event": {"pane": <pane as listed>,
  "kind", "text"}}` without an `id`. The hub takes the host from the
  connection, checks every field and drops what does not fit: `kind` from
  the list above, `text` without control characters and at most 200
  characters, `pane.pane_id` as `%<digits>`, an exposed mode. At most 10
  events a second per agent.

## Versioning

The path carries the version. Additions that old clients can ignore (new
fields, new endpoints) stay in v1; anything else is v2, served next to v1
for a transition period.

### Feature detection

Within v1 a client learns what this hub and each host take by asking, not
by version number:

| What | How a client learns it |
|---|---|
| a transcriber | `GET /v1/transcribe`: `204` yes, `404 not_found` no |
| files for a pane | `GET /v1/panes/{address}/files`: `204` yes; `403 read_only` the pane is not writable for you; `404 not_found` no inbox on that host (or no such pane) |
| the key grammar under `input` | `hosts[].keys` is `2`; absent, only the earlier named keys, and `400 bad_input` for the rest |
| a `count` with a key under `input` | `hosts[].repeat` is true; absent, send the key once per press |
| new sessions on a host | `hosts[].sessions` is true |
| closing panes on a host | `hosts[].close` is true |
| a newline in `text` | a hub older than that answers `400 bad_input`; send a line at a time to be safe |
| an identity provider | `GET /v1/auth`: `methods` holds `oidc` |
| the admin grant | `GET /v1/me`: `"admin": true` |

A flag absent from `hosts[]` means the host's agent does not take the
feature; an endpoint this hub does not know answers `404 not_found`, the
same code as a pane the token may not see, so a client treats a `404` on
a probe as "not here" and nothing more.
