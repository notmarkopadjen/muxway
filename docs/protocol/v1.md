# Protocol v1

Everything a client needs to talk to a muxway hub. All examples use
placeholder names.

## Transport and authentication

- HTTPS only (a hub accepts plain HTTP on loopback alone, behind a proxy).
- Every client request carries `Authorization: Bearer <token>`. Tokens look
  like `mxt_` followed by 43 URL-safe characters and are issued by the hub
  owner with `muxway hub token create`.
- Clients whose network stack rewrites `Authorization` send the token in
  `X-Muxway-Token: <token>` instead. WAP 1.x phones are such clients: their
  stack knows only the Basic scheme and re-encodes a Bearer header as Basic.
  A request may carry both headers only if they hold the same token.
- Tokens never go in URLs.
- A page on another origin, such as a glasses app's WebView, may call the
  client endpoints with a bearer token: the hub answers CORS preflights on
  `/v1/hosts`, `/v1/panes`, `/v1/events`, `/v1/windows` and `/v1/me` with
  `Access-Control-Allow-Origin: *`, the methods `GET` and `POST`, the
  headers `Authorization`, `X-Muxway-Token`, `Content-Type`, `Accept` and
  `If-None-Match`, and exposes `ETag`. It never allows credentials, so a
  session cookie is of no use to another origin, and the sign-in and
  agent endpoints answer no preflight.
- A browser signs in once instead and gets a **session cookie**,
  `muxway_session` (HttpOnly, Secure, SameSite=Strict). The hub honours it
  only when the request also carries an `X-Muxway-Client` header with any
  value. See [signing in](../features/sign-in.md).
- A hub may keep **address lists** (allow and deny). A request from an
  address they refuse is answered `403 forbidden` before anything else,
  credentials included. See [the admin overview](../features/admin.md).

## Responses

- JSON by default. Send `Accept: text/plain` for **text mode**, meant for
  small clients: no colours, tabs expanded, trailing blanks trimmed, lines
  rewrapped to `width`.
- Errors are `{"error": "<code>"}`:

| Status | Code | Meaning |
|---|---|---|
| 400 | `bad_json`, `bad_input`, `bad_parameter` | malformed request, text with control characters, unknown key, parameter out of range |
| 401 | `unauthorized` | missing, wrong, expired or revoked token (never says which) |
| 403 | `read_only`, `no_account`, `forbidden` | the pane is readable but the token or the pane's mark does not allow writing; a verified identity with no user on this hub; the address lists refuse the client, or an admin endpoint was called without the admin grant |
| 404 | `not_found` | no such host or pane, **or one the token may not see** |
| 409 | `exists`, `too_many`, `self_lockout` | see the endpoint |
| 413 | `too_large` | body over 16 KiB |
| 429 | `locked_out`, `rate_limited` | 10 failed authentications from an address in 10 minutes lock it for 10 minutes; a token may make 20 requests per second |
| 502 | `provider_unavailable` | the identity provider could not be reached |
| 503 | `host_offline` | the host's agent is not connected |

## Signing in

| Method and path | Purpose |
|---|---|
| `GET /v1/auth` | no authentication; `{"methods": ["token", "oidc"], "oidc": {"label": "Sign in with Example"}}`; `methods` is `["token"]` on a hub without a provider |
| `POST /v1/auth/token` | `{"token": "mxt_..."}`; sets the session cookie; `204`, or `401` which counts toward the lockout |
| `GET /v1/auth/oidc/start` | redirects to the identity provider |
| `GET /v1/auth/oidc/callback` | the provider's return; sets the cookie and answers a page that continues to `/` (a redirect would still be a cross-site navigation, on which browsers withhold a `SameSite=Strict` cookie); `401 sign_in_failed`, `403 no_account` or `502 provider_unavailable` |
| `POST /v1/auth/logout` | ends the session; `204` |
| `GET /v1/me` | `{"id": "0ddba4b5", "name": "phone", "method": "token", "read": [...], "write": [...], "expires": 1767225600}` |

`method` is `token` for a pasted token or the provider's name; `expires` is
when the session ends; `"admin": true` is there only for a principal with
the admin grant. Every endpoint below accepts the session cookie
with the header in place of the bearer token.

## Addresses

`<host>/<session>/<window>.<pane>`: host alias (`[a-z0-9-]{1,32}`), session
name, window index or name, pane index. Session and window names in a
request may use `[A-Za-z0-9._-]{1,64}`; a name with other characters is
reached by window index. A pane with an alias is also `<host>/@<alias>`.

## Endpoints

### `GET /v1/hosts`

Hosts the token has a read grant on, whether connected or not.

```json
{"hosts": [{"name": "alice-laptop", "online": true, "sessions": true}]}
```

`sessions` is present, and true, when the host's agent runs with
`--allow-sessions`, so a client may start a session there (see
`POST /v1/hosts/{host}/sessions`). Text mode: `alice-laptop<TAB>online`
per line.

### `GET /v1/panes`

Every pane the token can read, on every connected host, sorted by host,
session, window and pane.

```json
{"panes": [{
  "host": "alice-laptop", "address": "alice-laptop/work/1.0",
  "session_id": "$0", "session": "work",
  "window_id": "@1", "window_index": 1, "window": "logs",
  "window_layout": "b25d,100x30,0,0,1", "window_active": true,
  "pane_id": "%3", "pane_index": 0, "pane_active": true,
  "width": 100, "height": 30, "title": "build", "command": "bash",
  "activity": 1767225600, "mode": "write", "alias": "logs"
}]}
```

`mode` is what *this token* may do: `write` only when both the pane's mark
and the token allow it. `window_layout` is tmux's layout string for the
window. A pane that needs its owner also carries
`"attention": {"kind": "question", "at": 1767225600, "text": "..."}` with
`kind` one of `question`, `permission`, `idle`, `done`; see
[notifications](../features/notifications.md). Text mode:
`<address><TAB><mode><TAB><command><TAB><title><TAB><kind>`, the last
column empty when nothing is pending. `title` is what the program in the
pane calls itself (tmux's pane title), `command` the program's name. Text
mode takes `charset` as a pane read does: `command` and `title` are
rewritten for the charset and the body is encoded in it; the other
columns are ASCII already.

### `GET /v1/hosts/{host}/tree`

One host as sessions, windows (with layout) and panes, nested:

```json
{"host": "alice-laptop", "sessions": [{"name": "work", "windows": [
  {"index": 0, "name": "editor", "layout": "...", "active": false, "panes": [ ... ]}
]}]}
```

### `GET /v1/panes/{address}`

Query: `lines` (1 to 2000, default 100), `width` (8 to 400, default 80,
text mode), `charset` (text mode: `utf-8`, the default, `latin1` or
`ascii`), `ansi=1` (JSON only: keep colour escape sequences).

```json
{"pane": { ...as in the list... }, "content": "$ make test\nok\n"}
```

Text mode returns the last `lines` lines after rewrapping. With `latin1`
or `ascii` the hub first rewrites what the charset cannot carry (see
[text mode](../features/text-mode.md)): box-drawing lines become `-`,
`|` and `+`, bullets `*`, arrows `>` and `<`, letters lose the marks the
charset lacks, and the rest becomes `?`. The body is then encoded in that
charset and `Content-Type` names it: `text/plain; charset=utf-8`,
`charset=iso-8859-1` or `charset=us-ascii`. A hub without this
parameter ignores it and answers UTF-8, so decode by the `Content-Type`
you receive. Responses carry an `ETag`; send it back in `If-None-Match`
to get `304` when nothing changed, which keeps polling cheap on slow
links.

### `POST /v1/panes/{address}/input`

Body, exactly one of:

```json
{"text": "make test"}
{"key": "Enter"}
{"mouse": {"button": "left", "x": 12, "y": 3}}
```

- `text`: UTF-8, 1 to 4096 bytes, no control characters (C0, DEL, C1),
  except the newline. A text without a newline is typed literally. A text
  with one is **pasted**: the agent loads it into a tmux buffer and pastes
  the buffer into the pane, wrapped in the bracketed-paste marks when the
  program asked for them (`ESC [ 200 ~` … `ESC [ 201 ~`, written by tmux,
  never accepted from a client), so Claude Code or a readline shell takes
  the lines as one block and waits; a program that did not ask gets the
  bytes as typed, and a shell without bracketed paste runs each line at
  its newline. Send `Enter` separately either way. Carriage return and
  tab stay refused. A hub older than this answers `400 bad_input` to a
  newline.
- `key`: one of `Enter`, `Tab`, `BTab`, `BSpace`, `Escape`, `Space`,
  `Up`, `Down`, `Left`, `Right`, `PageUp`, `PageDown`, `Home`, `End`,
  `Insert`, `Delete`, `C-c`, `C-d`, `C-z`, `C-l`, `C-a`, `C-e`, `C-u`,
  `C-k`, `C-w`, `C-r`, `C-x`, `C-n`, `C-p`, `C-f`, `F1` to `F12`. The
  names are tmux's (`Insert` and `Delete` reach it as `IC` and `DC`);
  `BTab` is Shift-Tab, which AI coding CLIs use to cycle their modes.
  A hub older than this refuses the names added after `C-l` with
  `400 bad_input`.
- `mouse`: a click, press and release, or one wheel notch, at a cell of
  the pane: `button` one of `left`, `middle`, `right`, `wheelup`,
  `wheeldown`; `x` and `y` 1-based, within the pane's width and height.
  It reaches the program only when it asked its terminal for the mouse:
  the listing says so with `"mouse": true`, and the agent answers
  `bad_input` otherwise, so the bytes are never typed as text. The agent
  writes the xterm sequence in the encoding the program chose, SGR or
  the old one (which reaches cell 223 at most).

Answers `204` on success. A hub without mouse input answers `400
bad_json` to the third shape.

### `GET /v1/events`

Notifications from panes the token may read, oldest first. Query: `after`
(the `next` of the previous answer; without it, the most recent events),
`wait` (0 to 30 seconds to hold the request until an event arrives,
default 0), `limit` (1 to 100, default 50).

```json
{"events": [{
  "seq": 12, "at": 1767225600,
  "host": "alice-laptop", "address": "alice-laptop/work/1.0",
  "pane_id": "%3", "alias": "build",
  "kind": "permission", "text": "Claude needs your permission to use Bash"
}], "next": 12}
```

- `kind` is `question`, `permission`, `idle`, `done` or `working`; the last
  clears the pane's attention.
- `next` is the cursor for the next call, also when `events` is empty. A
  cursor the hub does not know (it restarted) counts as absent.
- With `wait`, the answer comes as soon as there is an event the token
  may see, or empty when the time is up.
- Text mode: `<seq><TAB><at><TAB><address><TAB><kind><TAB><text>` per
  event, then `next<TAB><seq>`.

### `GET /v1/transcribe` and `POST /v1/transcribe`

Spoken clips to text, for clients with a microphone: the glasses, the
browser and the phone among them. A hub has a transcriber only when its
owner configured one (`muxway hub
serve --stt-url ...`, see [transcription](../features/transcription.md));
`GET` answers `204` when it has one and `404 not_found` otherwise, so a
client knows whether to offer the action.

`POST` takes `Content-Type: audio/wav`, a 16 kHz mono 16-bit PCM WAV of
at most 4 MiB and at least half a second, from a principal with at least
one write grant (the text exists to be typed). The hub forwards the clip
to the transcriber and answers the text it heard, cleaned of control
characters and cut to 4096 bytes, which is what input takes:

```json
{"text": "run the tests again"}
```

Text mode: the text, one line. Errors: `400 bad_input` (not such a WAV,
or too short), `403 read_only` (no write grant), `404 not_found` (no
transcriber), `413 too_large`, `429 rate_limited` (one clip per five
seconds per principal, on top of the general limit), `502
provider_unavailable` (the transcriber failed or took over 90 s). The
clip is kept in memory for the request only; the audit log records who,
how many bytes and seconds, and the result, never the text.

### `POST /v1/panes/{address}/resize`

Sizes the pane on the host, as a terminal would, or gives it back to
tmux. Body, exactly one of:

```json
{"cols": 140, "rows": 32}
{"cols": 140, "rows": 32, "scope": "window"}
{"cols": 140, "rows": 32, "scope": "window", "layout": "b25d,1000x1000,0,0[1000x750,0,0,3,1000x250,0,0,4]"}
{"cols": 140, "rows": 32, "scope": "window", "zoom": true}
{"fit": "auto"}
```

Without a scope, or with `"scope": "pane"`, the **pane** becomes
`cols × rows`: on an axis the pane spans its window, the window is sized;
on an axis it shares with neighbours, they give or take, and the window
grows before any pane of it would go under 20 columns or 5 rows. With
`"scope": "window"`
the pane's whole **window** is sized and its panes keep the proportions
they had (tmux's own resize would not keep them), or, with a `layout`,
take the proportions of that layout: a tmux layout string (as the window
endpoint returns it) whose sizes are read as weights and scaled to
`cols × rows`, so a client sends the splits it shows, in any unit. The
layout must name exactly the window's panes, is at most 2048 bytes, and
goes with the window scope only. With `"zoom": true`, window scope only,
the pane is then shown alone in its window, as tmux's own zoom does; a
window resize without it undoes a zoom. The listing marks the pane shown
alone with `"zoomed": true`; its size is then the window's, the layout
string still the one underneath. `fit: auto` releases all of it: the
window returns to automatic sizing, unzoomed, and the panes to the layout
they had before the first resize.

Needs a write grant and a pane marked for writing, like input: the person
at the host sees the change. `cols` 20 to 500, `rows` 5 to 300. Answers
`200` with `{"pane": {...}}` as the listing shows the pane afterwards,
`400 bad_parameter`, `403 read_only`, `404`, `429 rate_limited` for more
than one resize per second on the same window, or `503`.

### `GET /v1/windows/{host}/{session}/{window}`

One window, every pane of it the principal may read, with content, in one
request. Query `lines` (1 to 2000, default 100) and `ansi=1`.

```json
{"host": "alice-laptop", "session": "work",
 "window": {"index": 1, "name": "logs", "layout": "b25d,100x30,0,0{50x30,0,0,3,49x30,51,0,4}", "active": true},
 "panes": [{"pane": {...}, "content": "..."}]}
```

`layout` is tmux's layout string: a checksum, then cells `WxH,X,Y` that are
a pane (`,id`) or a split with children in `{...}` (side by side) or
`[...]` (stacked). A pane outside the grants is absent from `panes` but
still named in the layout. Carries an `ETag`; `304` on `If-None-Match`.
JSON only.

### `POST /v1/windows/{host}/{session}/{window}/panes`

Adds a pane to the window, as `tmux split-window` would. Body:

```json
{"direction": "h"}
```

`h` puts the new pane beside the pane it is split from, `v` below it. The
source is the window's active pane when the principal may type into it,
else the first pane of the window it may; the new pane opens in the
source's directory with the host's shell, and the host's focus stays where
it was. A mark set on the source pane itself is copied onto the new pane;
a mark on the window or session covers it already. The principal then
needs a write grant that covers the **new** pane's address: when it does
not, the hub closes the pane again and answers `403 read_only`, so a grant
for `alice-laptop/work/1.0` alone never gets a sibling.

Answers `201` with `{"pane": {...}}` as the listing shows the new pane,
`400 bad_input`, `403 read_only` (no writable pane in the window, or the
new pane outside the grant), `404 not_found`, `409 too_many` when the
window has 8 panes, `429 rate_limited` for more than one creation (pane or
session) per two seconds by the same principal, a refused one included, or
`503 host_offline`.

### `POST /v1/hosts/{host}/sessions`

Starts a detached session with the host's shell, when the host's agent runs
with `--allow-sessions`. Body:

```json
{"name": "scratch"}
```

The name is `[a-z0-9_-]{1,32}` and must not exist. The agent marks the
new session `@muxway-mode = write`, so it is exposed like any other and
`muxway exposed` lists it. The principal needs a write grant that covers
`host/<name>/*` (checked on the name before asking, and on the first pane
after).

Answers `201` with `{"pane": {...}}`, the session's first pane, `400
bad_input`, `403 read_only`, `404 not_found` when the host does not start
sessions, `409 exists`, `409 too_many` after 32 sessions started this way
that still live, `429 rate_limited` as above, or `503 host_offline`.

## Admin

Not for ordinary clients: these need a principal with the admin grant
(`--admin` on `muxway hub token create` or `user create`) and answer
`403 forbidden` to any other. They take the bearer token or the session
cookie with the client header, and answer no CORS preflight. See
[the admin overview](../features/admin.md).

| Method and path | Does |
|---|---|
| `GET /v1/admin/overview` | the hub's facts, agents, tokens, users, clients, locked addresses, the address lists, and the caller's address as the hub sees it |
| `GET /v1/admin/log?after=N&limit=200&wait=0` | log records after `N` (without `after`, the latest), `limit` 1 to 500, long-polled up to `wait` seconds (at most 30) like `/v1/events` |
| `POST /v1/admin/tokens` | `{"name", "read", "write", "ttl", "admin"}`, `ttl` in seconds (0: 30 days, or 24 h with `admin`); `201 {"secret", "token"}`, the secret only here |
| `DELETE /v1/admin/tokens/{id}` | revoke; its sessions end at once; `204` or `404` |
| `POST /v1/admin/users` | `{"email", "name", "read", "write", "ttl", "admin"}`; `201 {"user"}` |
| `DELETE /v1/admin/users/{id}` | remove; its sessions end; `204` or `404` |
| `DELETE /v1/admin/sessions/{id}` | end one browser session, named by its `id` in the overview; `204` or `404` |
| `PUT /v1/admin/access` | `{"allow": [...], "deny": [...]}`, CIDRs or addresses, at most 256 each, body up to 64 KiB; answers the stored, normalised lists; `400 bad_input`; `409 self_lockout` when the caller's own address would be refused, unless `?force=1` |
| `POST /v1/admin/unlock` | `{"addr"}` lifts a lockout; `204`, `400`, or `404` when it was not locked |

`GET /v1/admin/overview`:

```json
{
  "hub": {"version": "1a2b3c4d5e6f", "tls": true, "trust_proxy": false, "providers": ["oidc"],
          "transcriber": false, "web": true, "public_url": "https://hub.example.com", "session_ttl": 43200},
  "agents": [{"host": "alice-laptop", "online": true, "paired": 1767225600, "connected": 1767229200, "addr": "192.0.2.10"}],
  "tokens": [{"id": "0ddba4b5", "name": "phone", "read": ["alice-laptop/*"], "write": [], "admin": false,
              "created": 1767225600, "expires": 1769817600}],
  "users": [{"id": "1c6eb20e", "email": "alice@example.com", "name": "", "read": ["*"], "write": ["*"], "admin": true,
             "created": 1767225600, "expires": 1798761600}],
  "clients": [
    {"kind": "session", "id": "Xq3kP0aZ", "client": "web", "principal": "1c6eb20e", "method": "oidc",
     "addr": "198.51.100.7", "since": 1767229000, "seen": 1767229300, "expires": 1767272200},
    {"kind": "bearer", "client": "muxway-android", "principal": "0ddba4b5", "method": "token",
     "addr": "198.51.100.8", "since": 1767228000, "seen": 1767229290}
  ],
  "locked": [{"addr": "203.0.113.9", "until": 1767229800}],
  "access": {"allow": [], "deny": ["203.0.113.0/24"]},

```

A client's type is its `X-Muxway-Client` header, or the first word of its

`GET /v1/admin/log?after=41`:

```json
{"records": [
  {"seq": 42, "at": 1767229300, "level": "INFO", "msg": "signed in",
   "attrs": {"addr": "198.51.100.7", "method": "token", "token": "0ddba4b5"}},
  {"seq": 43, "at": 1767229302, "level": "WARN", "msg": "authentication failed",
   "attrs": {"addr": "203.0.113.9", "path": "/v1/panes"}}
], "next": 43}
```

The log is the hub's own, the last 2000 records at Info and above, in
memory; `seq` starts over with the hub.

## Agent channel

For agent implementers only; clients never see it.

- `POST /v1/pair` with `{"code_id", "host", "agent_key", "proof"}` where
  `proof = base64url(HMAC-SHA256(secret, "muxway-v1-pair\0" + host + "\0" + agent_key_bytes))`.
  The answer `{"sig"}` is the hub's Ed25519 signature over
  `"muxway-v1-paired\0" + host + "\0" + agent_key_bytes`.
- `GET /v1/agent` upgrades to a WebSocket of binary messages. Handshake:
  `hello {v, nonce, eph}` from the hub; `{host, nonce, eph, sig}` from the
  agent; `{sig}` from the hub. Signatures are Ed25519 over
  SHA-256(`"muxway-v1-agent\0"` or `"muxway-v1-hub\0"`, host, `\0`, then hub
  nonce, hub ephemeral key, agent nonce, agent ephemeral key, each prefixed
  with its 4-byte big-endian length). Keys: HKDF-SHA256 over the X25519
  secret, salt = hub nonce + agent nonce, info `muxway-v1 hub to agent` and
  `muxway-v1 agent to hub`, 32 bytes each, AES-256-GCM with a 96-bit nonce
  that is a per-direction counter starting at 0.
- Then the hub sends `{"id", "op": "list" | "read" | "input" | "resize", "actor",
  "pane", "lines", "ansi", "text", "key", "mouse"}` and the agent answers
  `{"id", "error", "panes", "content"}` with error codes `not_exposed`,
  `read_only`, `bad_input`, `unknown_op`, `tmux_error`.
- `resize` is a fourth op: `{"id", "op": "resize", "actor", "pane",
  "cols", "rows", "scope", "layout", "zoom"}` (`scope` absent or `"pane"`,
  or `"window"`; `layout` and `zoom` only with `"window"`) or
  `{..., "fit": "auto"}`,
  answered like `input`, with `rate_limited` among the errors. The agent
  checks the layout itself: it parses and names the window's panes, no
  more and no fewer, or the answer is `bad_input`.
- `split`, `new-session` and `kill-pane` make and unmake panes:
  `{"id", "op": "split", "actor", "pane", "direction": "h" | "v"}` splits
  an exposed, writable pane and answers `{"id", "pane": <the new pane as
  listed>}`, or `read_only`, `too_many` (8 panes in the window),
  `bad_input`; `{"id", "op": "new-session", "actor", "name"}` answers the
  session's first pane, or `not_allowed` (the agent runs without
  `--allow-sessions`), `exists`, `too_many` (32 live sessions it started),
  `bad_input`; `{"id", "op": "kill-pane", "actor", "pane"}` closes a pane
  the agent made within the last 30 seconds and nothing else
  (`not_exposed` otherwise). An agent that starts sessions says so with
  `"sessions": true` in every `list` answer.
- The agent may also send, unasked, `{"event": {"pane": <pane as listed>,
  "kind", "text"}}` without an `id`. The hub takes the host from the
  connection, checks every field and drops what does not fit: `kind` from
  the list above, `text` without control characters and at most 200
  characters, `pane.pane_id` as `%<digits>`, an exposed mode. At most 10
  events a second per agent.

## Versioning

The path carries the version. Additions that old clients can ignore (new
fields, new endpoints) stay in v1; anything else is v2, served next to v1
for a transition period.
