# Feature: new panes and sessions from a client

> Status: approved by the owner on 2026-10-24. Asked for
> as "an option to add panes / sessions: a + after the pane list, and a
> + session button at the top right".

## 1. Goal

A client can only type into panes that exist. Starting a second Claude
Code next to the first, or a fresh session for a new piece of work, needs
the host's keyboard. This lets a client **split** a writable window into
one more pane, and **start a session**, within what the token may write
and what the host owner allowed. The pane list gets `+ pane` under each
window's panes and `+ session` at its top right, on the web and on the
phone.

Out of scope: closing panes or sessions from a client (`exit` does it);
choosing a command for the new pane (it runs the host's shell, the
command row then offers `claude`); windows (a session's first window
comes with it; more windows is a later step).

## 2. Design

**A new pane** is a `split-window` of a window the token may write. The
agent splits the window's active pane (`-t <window>`, `-c` the source
pane's directory, horizontal or vertical by the client's choice) and
copies a pane-level `@muxway-mode` from the source pane onto the new one
when the source's mark is on the pane itself; a mark on the window or
session already covers the new pane, as the exposing page says. The hub
then checks the new pane's address against the principal's write grant
and, when it does not match, has the agent kill the pane and answers
`403 read_only`: a token for `alice-laptop/work/1.0` alone gets no
sibling.

**A new session** is `new-session -d -s <name>` with the host's default
shell, allowed only when the agent runs with `--allow-sessions` (default
off): the agent then marks the session `@muxway-mode = write`, which is
the owner's standing decision that sessions clients start are theirs to
use. The hub requires a write grant matching `host/<name>/*` before
asking; the name is `[a-z0-9_-]{1,32}`, must not exist, and is the
person's own.

```mermaid
sequenceDiagram
    participant C as Client
    participant H as Hub
    participant A as Agent
    C->>H: POST /v1/windows/{host}/{session}/{window}/panes {"direction": "v"}
    H->>H: write grant on the window's panes?
    H->>A: OpSplit {window, direction}
    A->>A: split-window; copy a pane mark
    A-->>H: the new pane
    H->>H: grant covers its address? else OpKill
    H-->>C: {"pane": {...}} (201)
    C->>C: open it
```

**Web.** Under each window's rows in the list, a dim `+ pane` row (shown
when the window has a writable pane); a click splits (vertical on a tall
window, horizontal on a wide one, as the host shows it) and opens the new
pane. `+ session` in the list's top right opens a one-line form for the
name (`Esc` cancels, `Enter` creates), then opens the session's pane;
shown only for hosts that allow it (`GET /v1/hosts` says
`"sessions": true` per host). Keys: `+` on a selected window row, `S` for
a session. The selector (`p`) lists `+ session on <host>` too.

**Android.** The same `+ pane` row and a `+ session` in the list's top
row; the form is a small dialog.

## 3. Protocol and API changes

| Method and path | Body | Answer |
|---|---|---|
| `POST /v1/windows/{host}/{session}/{window}/panes` | `{"direction": "h" or "v"}` | `201 {"pane": …}`; `403 read_only`; `404`; `503 host_offline`; `409 too_many` when the window has 8 panes |
| `POST /v1/hosts/{host}/sessions` | `{"name": "scratch"}` | `201 {"pane": …}` (the first pane); `403 read_only` without the grant; `404 not_found` when the host does not allow it; `409 exists`; `400 bad_input` |
| `GET /v1/hosts` | | each host gains `"sessions": true` when its agent allows new sessions |

Agent ops `split`, `new-session`, `kill-pane` (the hub's undo only).
One creation per two seconds per principal. Compatible additions.

## 4. Security analysis

- **What is new.** A client can start shells, not only type into them.
  A new pane runs as the host's user in a window the token may already
  write to, which is the same power as typing `tmux split-window` into
  that pane; the grant check on the new address keeps a one-pane token
  one-pane. A new session is more: a shell where nothing was exposed, so
  it needs the owner's `--allow-sessions` and a write grant for that
  session name, and it is marked by the agent, in the open, as
  `@muxway-mode`, so `muxway exposed` lists it like any other.
- Names: validated on the hub and again on the agent; passed to tmux as
  arguments, never through a shell; `-d` so nothing attaches.
- Caps: 8 panes per window, 32 sessions per host started this way (the
  agent counts sessions it marked), one creation per two seconds per
  principal; a failed creation costs the slot too.
- Audited: who, host, window or name, result, the new pane id.
- The undo (`kill-pane` when the grant does not cover the result) is the
  hub's alone; a client has no kill.
- No new dependencies.
