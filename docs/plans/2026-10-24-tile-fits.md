# Feature: tiles that do not fight, and fits that outlive a switch

> Status: the owner reported the symptoms on 2026-10-24 (a tile of one
> window cropped at 157 columns inside a 97-column box, the two tiles
> breathing; a pane shown alone re-fitting every time `[` `]` come back to
> it) and, on the diagnosis below, said "fix all". Closes muxway#48 and
> muxway-android#3.

## 1. Goal

Two tiles that are panes of one tmux window each fit their own pane, and
on the host a pane's size is taken from its row: the second fit undoes
the first, the loser shows 157 columns in a 97-column box with its text
cut, and when both retry the row breathes. And with one pane open, `]`
replaces the tile: the old tile's fit is released on the way out, tmux
puts the pane back to its layout size, and coming back fits it again,
visibly. The goal: tiles of one window never pull its row both ways, a
pane shown alone is sized without touching its neighbours, and moving
between panes in the pane view leaves each at the size it was given.

Out of scope: the window view and boards, which keep their fits as they
are; a fit the host did not keep (another terminal holds the window),
which the tile reports as before.

## 2. Design

**One fit per window (both clients, muxway#48, muxway-android#3).** Among
the open tiles, those that are panes of one window share one fit: the
focused tile's pane fits (pane scope), or, when the focus is in another
window, the first of them. The others of that window keep fit off and
say *held* in their header; their screen is drawn scaled to the box, so
nothing is cropped. Focus moving to another tile of the window moves the
fit: the previous tile releases, the new one fits.

**A pane alone fits the window, zoomed (web).** With one tile open the
fit is window scope with `zoom`: the window takes the box's size and the
pane is shown alone in it, as tmux's own zoom does, so its neighbours
are not squeezed to the floor and switching between siblings of one
window moves the zoom instead of re-laying the row. A pane whose window
has no other pane is fitted at window scope without zoom (tmux cannot
zoom a lone pane). Release puts the window back to automatic sizing,
unzoomed, as before.

**Fits outlive a switch (web).** A tile leaving the pane view no longer
releases its pane by itself: `useFit` keeps the address in a registry,
and the pane view releases every kept pane when it is left (the route
changes to the list, a board, the window view; or the page goes away).
A tile coming back to a kept pane whose size is already what the box
asks for, zoomed when a zoom is asked, sends nothing. Until the host
reports the fitted size, the tile shows the last frame it had of that
pane at that size, kept per address, instead of the smaller frame of the
moment between.

```mermaid
sequenceDiagram
    participant B as Browser (pane view)
    participant H as Hub
    participant T as tmux
    B->>H: resize 0.0 {scope: window, zoom: true, cols, rows}
    H->>T: resize-window, select-layout, resize-pane -Z 0.0
    Note over B: ] shows 0.1 in the tile; 0.0 stays kept, not released
    B->>H: resize 0.1 {scope: window, zoom: true, cols, rows}
    H->>T: unzoom, resize-window (same size), resize-pane -Z 0.1
    Note over B: [ brings 0.0 back: window at size, 0.0 not zoomed → resize again, same size; the last frame of 0.0 shows meanwhile
    Note over B: Esc leaves the view
    B->>H: resize 0.0 {fit: auto}, resize 0.1 {fit: auto}
    H->>T: window automatic, unzoomed
```

## 3. Protocol and API changes

None. The window scope with `zoom` is in the protocol already.

## 4. Security analysis

- The same resize endpoint with the same grant (write on the pane); a
  held tile sends nothing. The registry of kept panes is in page memory
  and holds addresses only.
- A release on leaving the view and on `pagehide` is sent with
  `keepalive`, as before; nothing is logged beyond the resize audit line
  the hub writes already.
- No new dependencies.
